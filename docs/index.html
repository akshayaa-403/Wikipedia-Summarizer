Extractive vs. abstractive summarization · ROUGE evaluation

Most summarizers only read the first page.

BART accepts 1024 tokens. The average article body in this benchmark runs 6,700 words. Hand one to the other and the model silently discards about 90% of it, then summarizes the opening paragraphs as though they were the whole thing. This project reads the entire article instead — and then measures, with ROUGE, what that actually buys.

01 — The long-context problem

Truncation discards the article without telling you

The original version of this project did what almost every tutorial does: pass the article to the tokenizer with truncation=True and a 1024-token limit. That call never fails and never warns. It just quietly throws away everything past the cut and returns a fluent, well-formed summary of the article's introduction.

For Photosynthesis — ~6,600 words in the body — a single window covers roughly a tenth of the text. The light reactions make it in. The Calvin cycle, C4 and CAM pathways, and the entire evolutionary history section do not.

Baseline · truncate

One window, one pass

The tokenizer keeps the first 1024 tokens and drops the rest. Cost is one model call, and the summary can only ever describe the opening of the article. Nothing in the API signals that this happened.

This project · map-reduce

Every chunk read, then condensed

The body is packed into overlapping windows that break on sentence boundaries. Each is summarized (map), the summaries are concatenated and summarized again (reduce), repeating until the intermediate text fits one window. The final pass sees material from the whole article.

Two details that matter more than they look

Chunks break on sentence boundaries. Cutting mid-clause leaves an abstractive model to invent an ending for a severed sentence, which is how hallucinated facts get in.

Chunks overlap by one sentence. Without the carry, a fact introduced at the end of chunk n and referenced by a pronoun at the start of chunk n+1 leaves the second chunk summarizing a dangling "it" with no antecedent. That single-sentence overlap is what actually keeps context across the boundary.

What the benchmark actually shows

Map-reduce does not beat truncation on ROUGE. It reads 100% of the body against the baseline's 8.5%, takes 6.5× as long, and lands essentially level — slightly behind on ROUGE-1 and ROUGE-L, slightly ahead on ROUGE-2, winning 4 of 10 articles. Reading twelve times more text bought no measured gain on this metric. That is the result, and inventing a win the numbers don't show would make every other figure on this page worth less.

The metric is part of the reason. The reference is the article's lead section, and a lead is written to introduce the subject — it is topically closest to the article's opening, which is exactly the region truncation reads. So the reference quietly rewards the baseline for its handicap. A summary that faithfully covers the Calvin cycle, C4 pathways and evolutionary history is penalised for spending words on material the lead never mentions.

LexRank wins outright, and that is largely ROUGE measuring what ROUGE measures: lexical overlap. An extractive method copies Wikipedia's own sentences, so it reuses the reference's vocabulary by construction, while an abstractive model paraphrases and is marked down for it. ROUGE is a similarity metric, not a correctness metric, and it cannot see whether a summary is true.

What map-reduce does buy is coverage — the guarantee that no section was silently discarded. Whether that is worth 6.5× the compute depends on whether the task needs the whole article represented or just a fluent opening. This benchmark can size that trade-off; it cannot make the choice.

04 — Methods

What each method does

LexRank

extractive

Builds a graph whose nodes are sentences and whose edges are TF-IDF cosine similarity, then ranks by eigenvector centrality. Selects the highest-ranked existing sentences verbatim. No context limit — the whole article is one graph — and no risk of hallucination, but it can only ever reuse sentences the article already contains.

LSA

extractive

Applies singular value decomposition to the term–sentence matrix and picks the sentence that best represents each leading latent topic. Tends to produce more topically diverse selections than LexRank, and more erratic ones on articles with a strong single theme.

BART, truncated

abstractive · baseline

facebook/bart-large-cnn with truncation=True. Generates genuinely new sentences, fluently — but only about the first 1024 tokens. Included as the baseline precisely so the cost of truncation can be quantified rather than assumed.

BART, map-reduce

abstractive · this project

The same model and decoding parameters, applied hierarchically over overlapping sentence-aligned chunks until the condensed text fits a single window. Reads 100% of the body at the cost of one model call per chunk plus the reduce passes.

05 — Reproduce

Run it yourself

Everything on this page is generated by the code in the repository.

pip install -r requirements.txt
python -c "import nltk; nltk.download('punkt'); nltk.download('punkt_tab')"

# summarize one article with every method, scored against its lead
python -m wikisum "Photosynthesis" --evaluate

# regenerate the benchmark this page reads
python -m wikisum.benchmark --out docs/data/results.json

The benchmark runs BART on CPU; expect a few minutes per article. The live demo above needs none of it — it runs TextRank in your browser against the Wikipedia API directly, because GitHub Pages serves static files and cannot execute Python.
